`createClient` is the relying-party (RP) helper for kicking off OAuth
flows, exchanging codes, refreshing tokens, and verifying JWTs. It lives
at a dedicated import path for tree-shaking:

```ts
import { createClient } from "@_mustachio/openauth/client"

const client = createClient({
  clientID: "my-client",
  issuer: "https://auth.yourapp.com",
})
```

The helper is optional — any OAuth client library can talk to the IdP.
Use this when you want a thin typed wrapper without pulling another
dependency.

## Public vs confidential clients

A **public** client — a SPA, a mobile or desktop app, a CLI — ships to
users and cannot keep a secret, so it authenticates with PKCE alone. That
is the default: construct the client with a `clientID` only.

A **confidential** client is server-side code where a secret genuinely
stays secret. Pass `clientSecret`, and `exchange` and `refresh` will
authenticate at the token endpoint:

```ts
const client = createClient({
  clientID: "my-server-app",
  clientSecret: process.env.CLIENT_SECRET,
  issuer: "https://auth.yourapp.com",
  // "client_secret_basic" (default) or "client_secret_post"
  tokenEndpointAuthMethod: "client_secret_basic",
})
```

Without `clientSecret`, a confidential client's `exchange()` fails with
`invalid_client`: the token endpoint has no way to authenticate it.

## The flow

Identical for both kinds of client. **PKCE is always used** — the IdP
requires it for public clients, and OAuth 2.1 §7.5.1 recommends it for
confidential ones too — so `authorize()` always returns a `challenge`
whose `verifier` you must hand back to `exchange()`.

```ts
const redirectUri = "https://app.example.com/callback"

// 1. Start the flow and persist the challenge. Server-side, put it in a
//    short-lived signed cookie; in a SPA, sessionStorage.
const { challenge, url } = await client.authorize(redirectUri)
sessionStorage.setItem("challenge", JSON.stringify(challenge))
location.href = url // or Response.redirect(url, 302)

// 2. Back at your redirect URI with `?code=...`.
const saved = JSON.parse(sessionStorage.getItem("challenge")!)
const params = new URLSearchParams(location.search)

// `state` is your CSRF defence — compare it before exchanging.
if (params.get("state") !== saved.state) throw new Error("state mismatch")

const exchanged = await client.exchange(
  params.get("code")!,
  redirectUri,
  saved.verifier,
)
if (exchanged.err) throw exchanged.err

// 3. Verify on subsequent requests. If `refresh` is supplied, the helper
//    refreshes automatically when access has expired and returns the
//    rotated tokens to re-set on the client.
const verified = await client.verify(subjects, exchanged.tokens.access, {
  refresh: exchanged.tokens.refresh,
})
if (verified.err) throw verified.err
console.log(verified.subject.type, verified.subject.properties)
if (verified.tokens) {
  // Rotated — write these back to your cookies / storage.
}
```

Only the authorization code flow is supported. `response_type=token` (the
implicit flow) is removed in OAuth 2.1 and the IdP rejects it.

## Audience

`verify()` checks the token's `aud` against this client's `clientID`, so a
token minted for one relying party will not verify at another sharing the
same issuer.

If you requested a resource `audience` at `/authorize`, the IdP puts that
value in `aud` instead. A resource server verifying such a token names
itself:

```ts
const verified = await client.verify(subjects, token, {
  audience: "https://api.example.com",
})
```

## Verifying tokens on the API side

When your API receives a request with an access-token bearer:

```ts
const verified = await client.verify(subjects, bearerToken)
if (verified.err) {
  return new Response("Unauthorized", { status: 401 })
}
console.log(verified.subject.type, verified.subject.properties)
```

`verify` does full JWKS validation against the issuer's
`/.well-known/jwks.json`. It caches the JWKS internally.

## Validating manually with `jose`

If you'd rather not pull in the client helper, validate the JWT directly
— the library doesn't leak any helper types so manual validation is
fully supported. See [Subjects](/docs/reference/subjects/) §"Verifying
tokens downstream" for the `jose` pattern.

## What about the discriminated `verified.subject`?

`subjects` is the same schema record you passed to `createIdP`. The
helper's `verify` narrows `verified.subject` to the right shape based on
`verified.subject.type`:

```ts
const verified = await client.verify(subjects, accessToken)
if (verified.subject.type === "admin") {
  verified.subject.properties.roles // typed as string[]
} else if (verified.subject.type === "user") {
  verified.subject.properties.userId // typed as string
}
```

This is the main reason to use the helper over hand-rolling `jose`.

## Full API

`createClient(input: ClientInput): Client` returns:

```ts
type Client = {
  authorize(
    redirectUri: string,
    opts?: AuthorizeOptions,
  ): Promise<AuthorizeResult>
  exchange(
    code: string,
    redirectUri: string,
    verifier?: string,
  ): Promise<ExchangeSuccess | ExchangeError>
  refresh(
    refreshToken: string,
    opts?: RefreshOptions,
  ): Promise<RefreshSuccess | RefreshError>
  verify<T extends SubjectSchema>(
    subjects: T,
    accessToken: string,
    opts?: VerifyOptions,
  ): Promise<VerifyResult<T> | VerifyError>
}
```

See `packages/openauth/src/client.ts` for the full type surface (input
shape, error types, refresh / verify options).
